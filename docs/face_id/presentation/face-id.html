A neural network: multiply, add, repeat

No magic inside: the recognizer is 1.19 million numbers (“weights”) that its authors learned from photos. Running it means multiplying values by weights and adding them up, layer after layer.

Layer
One round of multiply-and-add like the one on the left, for every spot of the picture.
Block
Three layers as a team: widen, look at the neighbours, narrow.
Shrinking
The stem turns each 2 × 2 patch of pixels into one spot; each stage’s first block merges 2 × 2 spots into one.
Percentages: each part’s share of the recognizer’s time for one face (434 ms, traced on the board). The detector (network 1, 53,121 weights) works the same way.

02 · Neural networks

Smaller numbers, same answers

Networks are usually trained with 32-bit floating-point numbers, but the chip is much faster with small whole numbers. Espressif publishes MFN_S8_V1 already in 8-bit whole numbers, every tensor with one power-of-two scale. Our job: compute exactly what its file says.

Three kinds of numbers (one box = one bit)
Size of all recognizer weights
as 32-bit
4.7 MB
8-bit
1.26 MB
More than the 512 KB of fast memory, so the weights live in PSRAM.
One scale per tensor, a power of two
52× 2−6=0.8125a whole number, in units of 1/64
Rescaling a sum is then a shift of its bits: no division, no float. The camera pixels go in the same way: (x − 127.5) / 127.5, in units of 2−6.
Before, with our first recognizer, EdgeFace-XXS
It came in 32 bits and we shrank it ourselves. Try 1, 8 bits everywhere, failed: small rounding errors piled up block after block, like copying a copy of a copy (closeness to the original 0.95 on average, worst 0.89). Try 2 kept 16 bits for the values between layers: 0.9972 on average, worst 0.9955.
MFN_S8_V1 comes in 8 bits from Espressif, so there was nothing to shrink, only to reproduce.
Same answers: our firmware code against an independent interpreter of Espressif’s file
7,701of 7,701 LFW photos
bit for bit
The interpreter is part of our laptop toolkit and shares no code with the firmware. Accuracy on LFW: 99.27 % (slide 15).

02 · Neural networks

The chip’s secret weapon: the vector unit

Beside its normal core, the chip has a small vector unit: 8 “lanes” for 16-bit numbers, or 16 lanes for 8-bit numbers, side by side in one instruction. The maths was cheap. What cost time was carrying values out to memory and back.

Clock ticks per multiplication
0.40
in all of the recognizer’s 1×1 layers, loading the numbers included
60–100
ticks for one value’s trip out to memory and back, in plain code
The first versions sent every result out of the unit after each layer. Moving data took far longer than the multiplying. Now results are rounded inside the unit, and each block works on bands of seven rows that stay in the fast internal RAM: the 14 × 14 block takes 41 ms row by row, 31 ms through PSRAM, 21 ms in bands of seven.
What the 8-bit mode saved
~600→345 ms
All 1×1 layers of the recognizer: estimated on the 16-bit lanes, measured in the 8-bit mode. Same results, bit for bit.

03 · Performance

23× faster, one measured step at a time

With our first recognizer, EdgeFace-XXS: nine measured steps, and the results stayed bit-for-bit identical after each. The biggest single win was the most boring one: 32-bit sums instead of 64-bit (step 02) saved 3.7 s, 44 % of the whole gain.

“Alone”: the network by itself on the core. The detector went the same way: 1,568 → 99 ms. Today’s recognizer, MFN_S8_V1, does more than twice the work and takes 432 ms alone (next slide).

03 · Performance

Measure, don’t guess: the chip’s price list

Our estimates from reading the source code were 2 to 4 times too optimistic, every time. So we timed each operation on the board and read the machine code the compiler produced.

Measured cost: one square = one clock tick
Surprises found in the machine code
1The compiler moved a slow 64-bit conversion into the loop, so it ran for every single output value
2512 bytes of memory were cleared before every batch of work, though nothing read them
3Results were read out one byte at a time: 200 instructions for 40 bytes
4A helper we asked the compiler to inline became a real function call, once per value
Fixing these, plus packing the weights (EdgeFace-XXS):1,560→1,006 ms
Memory has a price, too: the PSRAM chip delivers about 40 MB/s, flash about 10 MB/s. A 3 × 3 depthwise layer costs 1.15 ticks per multiplication from internal RAM, 3.24 from PSRAM.

03 · Performance

The app around the networks

The camera has almost no buffer: its pixels must be collected within about 5 ms or they are lost. A network keeps the core busy for hundreds of ms. Juggling both is like never blocking a UI thread.

Core 0 over 200 ms
How we found the stalls
1The log showed 256 lost camera images in 81 s, and a third of all time gone. 2At the same moments, the motion sensor on the other core reported gaps. Why would it care? 3Core 0 also runs the clock that both cores rely on. The camera code waited for the camera at a moment when nothing else may run on core 0, not even that clock, so both cores froze. The fix: the camera code never waits; it comes back 2 ms later.

03 · Performance

Rust without an operating system

No operating system, no threads, no files: just our Rust code on the chip. What the language gave us, and where it pushed back.

What Rust gave us
One library, two machines
The same Rust code runs in the laptop’s tests and on the chip. That is what made the bit-for-bit check possible.
async/await, without an OS
Camera and screen run as an async task that a timer wakes every 2 ms. A small async runtime does it all.
Hardware as owned values
The app owns its camera, screen and touch handles. No other code can use them by accident.
Where it pushed back
The fast maths needs assembly
The vector unit (slide 12) is only reachable through hand-written assembly inside the Rust code.
A compiler of its own
The chip needs its vendor’s own Rust toolchain, and the strongest optimisation setting makes that compiler crash.
64-bit floats are slow here
Rust compiles them without complaint, but this chip has no hardware for them, so every calculation runs as slow software. One in the wrong place cost 32 ms per block. We use 32-bit floats.

04 · What we take away

Four lessons for the next team

1
Measure on the device
Our estimates were 2–4× off. The board’s own numbers never were.
2
Moving data costs more than maths
Keep values in fast memory and inside the vector unit.
3
Prove every change
A bit-for-bit check against the laptop made bold changes safe.
4
Read the model’s licence first
Ours was non-commercial. Swapping it cost a new set of kernels.
Next: put the second core to work. Its helper tasks leave it mostly idle, and sharing each layer between both cores could almost halve the time again. In the recognizer, two blocks (57 and 52 ms) and the stem (32 ms) still have room.
Why it matters beyond this demo
Private by design: faces are recognised on the device, not in a cloud.
Small, low-power hardware instead of a PC with a graphics card.
The same recipe fits other on-device AI: machine vision, sensors, medical devices.
Picture this
A lab instrument that recognises its operator and loads their settings. Offline, and no photo ever leaves the device.
“Measure, don’t guess.”
The rule behind every step from 8.8 s to under half a second.
